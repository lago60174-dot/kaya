# Décisions techniques

- **Stack** : Next.js 16 (App Router), TypeScript strict, Tailwind, Supabase, Vitest, Playwright, déployé sur Cloudflare Workers avec OpenNext (`@opennextjs/cloudflare`, compatible Next >= 16.4.5). Le build Workers est vérifié (`npm run build:cf`).
- **Polices système** : pas de police web. Pages plus légères sur Android d'entrée de gamme et connexion lente.
- **Couleurs** : orange `#F97316` pour les accents, `#C2410C` pour les boutons (texte blanc, contraste AA). Fond `#FFFBF5`, texte `#1F2937`.
- **Versions figées** : aucune version avec `^` dans package.json. `@types/node` en 22 pour suivre Node 22 et rester compatible avec Vitest.
- **Argent** : entiers FCFA uniquement (`lib/format.ts` refuse les décimales). Quantités arrondies à 3 décimales.
- **shadcn/ui** : les composants seront ajoutés au fil des étapes (utilitaire `cn` déjà en place), pour ne livrer que ce qui sert.
- **Mode sombre** : non prévu, thème clair lisible en plein soleil.

## Étape 2 : base de données

- **Prix d'achat dans `produit_couts`, coût figé dans `vente_lignes_couts`** : la RLS filtre des lignes, pas des colonnes. Mettre ces données dans des tables lisibles par le propriétaire seul garantit qu'un vendeur ne les voit jamais, même en interrogeant l'API directement.
- **`supabase/` au lieu de `db/`** : le dossier standard de la CLI Supabase contient migrations et `seed.sql`.
- **Écritures sensibles uniquement par fonctions SQL** (security definer) : ventes, annulations, remboursements, mouvements de stock, clôtures. Aucun droit d'écriture direct pour les utilisateurs sur ces tables. Les fonctions vérifient rôle et boutique elles-mêmes.
- **Paiements : un seul montant peut être omis**, il prend le reste à payer. Ce qui n'est pas payé devient un crédit (client obligatoire).
- **Remise** : le vendeur est limité au seuil ; le propriétaire n'a pas de plafond. « Forcer » (plafond de crédit) est réservé au propriétaire.
- **Annulation** : l'avoir rembourse en espèces tous les paiements espèces de la vente (y compris les remboursements de crédit liés). La caisse du jour le déduit.
- **Immutabilité** : triggers sur mouvements, paiements, avoirs, lignes de vente et journal (aucune modification ni suppression, même pour le service_role). Une vente ne change qu'une fois (valide vers annulée). Pas de suppression physique des données métier.
- **Plafond de crédit par défaut** : 100 000 FCFA (modifiable dans les paramètres).
- **Tests SQL avec PGlite** (PostgreSQL réel en mémoire) : un petit module imite `auth.uid()` et les rôles Supabase. Aucun serveur à installer pour lancer la CI.
- **Seed** : seule exception à l'immutabilité (il étale les dates des ventes sur 7 jours, avec `session_replication_role = replica`). Ne jamais l'exécuter en production.
- **Types TypeScript** : `npm run types` les génère depuis une base Supabase locale (nécessite la CLI Supabase et Docker).

### Limites connues de l'étape 2

- La concurrence est protégée par des verrous de lignes (`FOR UPDATE`, compteur verrouillé) mais PGlite n'a qu'une connexion : le test « deux ventes du dernier article » est séquentiel. À rejouer en parallèle sur une vraie base Supabase à l'étape 12.
- Un seul compte propriétaire par organisation pour l'instant, et un utilisateur n'appartient qu'à une organisation.

Tables `administrateurs_plateforme` et `affilies`, avec les fonctions `app_est_admin()` et `app_affilie_id()`. Un affilié ne voit que ses parrainages (l'identifiant de l'organisation, jamais ses données) ; l'administrateur ne lit aucune donnée de vente.

Un utilisateur ne peut interroger que sa propre organisation. Un plan masqué n'est lisible ni par un visiteur ni par une autre organisation.

- **`organisations.plan_code`** est le plan en vigueur ; `abonnements` porte le cycle de facturation. Ils seront synchronisés par les fonctions d'abonnement (étape 18).
- **Images** : `photo_url` remplacé par `image_cle` et `vignette_cle` (clés R2).
- **Seed** : la démo est en plan Business pour montrer toutes les fonctions ; comptes `admin@kaya.demo` et `affilie@kaya.demo` (code DEMO20). Filleuls, commissions et factures de démonstration arrivent aux étapes 18 à 20.

## Étape 3 : authentification, rôles, plans

- **Inscription et comptes créés par le serveur** : `auth.admin.createUser` (email confirmé d'office) puis `creer_organisation`. L'inscription directe par l'API Supabase est fermée (`enable_signup = false`) pour ne pas contourner Turnstile. Limite connue : l'email n'est pas vérifié au MVP (aucun envoi d'email prévu), à reconsidérer.
- **Mot de passe provisoire des vendeurs** : généré côté serveur (10 caractères lisibles), affiché une seule fois, marqueur `doit_changer_mot_de_passe` dans `app_metadata` (non modifiable par l'utilisateur). Toute page protégée renvoie vers `/mot-de-passe` tant qu'il n'est pas changé. Un vendeur désactivé est aussi bloqué côté Supabase Auth.
- **Défense en profondeur** : proxy (redirection des visiteurs), garde dans les pages et les actions (`exigerRole`, `decisionGarde` testée), RLS et triggers. **Risque** : OpenNext classe le proxy Node.js comme expérimental sur Cloudflare. Le proxy ne protège rien à lui seul ; s'il pose problème en production, le retirer ne crée aucune faille (mais la session ne sera plus rafraîchie automatiquement : prévoir alors un rafraîchissement côté client).
- **Cache Components (Next 16) : désactivé.** Sur Cloudflare Workers, `cacheComponents: true` fait planter chaque requête (« Worker's code had hung », Error 1101), même sur une page statique : reproduit en local avec `npm run preview`, et signalé en amont ([next.js#100122](https://github.com/vercel/next.js/issues/100122), correctif [opennextjs-cloudflare#1318](https://github.com/opennextjs/opennextjs-cloudflare/pull/1318) pas encore publié). Les `<Suspense>` autour de la lecture de session restent utiles pour le confort d'affichage. À réactiver quand le correctif sera publié et testé avec `npm run preview`.
- **Parrainage** : `/a/CODE` pose un cookie de 30 jours (premier contact, jamais écrasé) ; le code saisi à l'inscription l'emporte. Auto-parrainage refusé (même compte, téléphone ou email) et signalé. Un code inconnu ou un affilié non validé n'empêche pas l'inscription.
- **Turnstile** : vérification serveur, refusée en production si la clé secrète manque (échec fermé).
- **Déconnexion automatique** après 2 h d'inactivité (`lib/auth/inactivite.ts`).
- **Limites connues** : le chargement du profil (`server/auth/profil.ts`) et les actions Supabase ne sont pas couverts par des tests automatiques ici (pas de Supabase local) ; ils le seront par les tests de bout en bout de l'étape 12. L'espace administrateur et l'espace affilié (pages) arrivent aux étapes 19 et 20 : les rôles et les gardes existent déjà.

## Étape 4 : produits et stock

- **Migrations non encore déployées** : j'ai donc modifié la migration 3 (le reçu garde le nom affiché avec la marque) au lieu d'en ajouter une. **À partir du premier déploiement, plus aucune migration existante ne sera modifiée.**
- **Multi-marque** : une marque est une table (`marques`) ; chaque marque d'un même article est un **produit distinct** (« Ciment CPJ 42,5 · Dangote » et « … · CIMAF »), avec son stock, ses prix et ses alertes. Raison : le stock et le prix diffèrent réellement d'une marque à l'autre, et le vendeur choisit une marque précise. Le nom affiché (`nom_affiche`) et la recherche (`nom_recherche`, sans accents, marque comprise) sont tenus à jour par déclencheur, y compris quand on renomme une marque. Deux produits ne peuvent pas avoir le même nom et la même marque.
- **Multi-conditionnement** : un produit a autant d'unités de vente que nécessaire, chacune avec son facteur vers l'unité de base (ciment gris : sac de 50 kg ; ciment blanc ou colle : sac de 25 kg, de 5 kg ; peinture : pot, seau de 4 pots). Le stock reste compté en unité de base, ce qui évite les erreurs d'arrondi (1 kg sur 50 kg = 0,02 sac). Le formulaire propose les conditionnements courants selon l'unité de base (`lib/stock/unites.ts`).
- **« Même produit, autre marque »** : copie les unités, l'unité de base et le prix d'achat d'un produit pour en créer un autre sans tout ressaisir (la photo, le stock et la marque ne sont pas copiés).
- **Limite assumée** : un conditionnement non divisible (un sac de 5 kg qu'on ne peut pas ouvrir) partage quand même le stock en kg avec les autres conditionnements du même produit. Si un client a besoin de stocks séparés par conditionnement, on créera un produit distinct.
- **Fiche produit atomique** (`enregistrer_produit`) : produit, prix d'achat et unités dans une seule transaction. Une unité retirée est archivée (les ventes y font référence). L'unité de base ne peut plus changer dès qu'il existe un mouvement de stock.
- **Liste paginée par curseur** (`lister_produits`) : 30 par page, stock de la boutique inclus, jamais de prix d'achat. Recherche sans accents ni casse, filtres catégorie, marque et stock bas.
- **Photos** : voir `docs/R2.md`. Compression dans le navigateur, envoi par URL signée de 5 minutes, contrôle du fichier après envoi.
- **Prix d'achat et marge** : visibles du propriétaire seulement (table séparée, RLS).
- **Non fait ici** : e2e du parcours photo (étape 12) ; la compression réelle dans le navigateur (canvas) n'est pas testable en Node, seule sa logique l'est (algorithme de qualité, dimensions, empreinte).

## Étape 5 : vente

- **Le serveur recalcule tout** : le navigateur n'envoie que des identifiants, des quantités, des modes de paiement et des montants de paiement. Prix, remises, total, numéro de reçu et stock sont calculés par `creer_vente`. L'aperçu du panier (`lib/ventes/panier.ts`) est un confort d'affichage : son arrondi est **vérifié contre PostgreSQL** (`tests/db/coherence.test.ts`, 135 combinaisons, y compris les .5).
- **Arithmétique exacte** : prix d'une ligne = quantité en millièmes x prix, en entiers (BigInt), arrondi au FCFA le plus proche comme `round()` en base. Aucun flottant dans les montants.
- **Idempotence liée au contenu** : la clé de la vente est tirée au sort une fois par contenu de panier. Un double clic ou un nouvel essai après coupure réutilise la même clé (jamais de doublon) ; si le vendeur modifie le panier entre deux essais, une nouvelle clé est créée, pour qu'une vente déjà enregistrée ne remplace pas silencieusement le nouveau contenu.
- **Paiements** : sans crédit, le dernier mode prend le reste ; avec crédit, ce qui n'est pas payé devient la dette du client (client obligatoire). Paiement mixte = plusieurs lignes. Le propriétaire seul peut dépasser le plafond de crédit.
- **Remise** : le vendeur voit son seuil et un message avant de valider ; la base applique la même règle (le seuil affiché n'est qu'une aide).
- **Marques** : chaque marque est un produit distinct dans la recherche (« Ciment CPJ 42,5 · Dangote » / « · CIMAF »), avec une pastille par unité (« + sac de 50 kg · 5 500 FCFA »). Un tap = une ligne ; un second tap sur la même unité = quantité + 1. La marque figure sur le reçu.
- **Écran de succès = reçu relu en base** (`/vente/recu/[id]`), pas une copie de l'écran : le vendeur voit exactement ce qui a été enregistré, et peut le rouvrir.
- **Partage WhatsApp** : lien `wa.me` vers le numéro du client depuis le téléphone du vendeur (aucun appel à Zernio). Le message résume le reçu, sans marge ni prix d'achat. Le lien vers la page publique du reçu et le PDF viennent à l'étape 6 : je n'ai pas mis de lien qui mènerait à une page inexistante.
- **Impression** : bouton `window.print()` affiché seulement si le plan autorise l'impression (Pro, Business), avec un style qui n'imprime que le reçu. Ticket 58 mm, A4 et RawBT : section 10 (voir « Section 10 : reçus, logo et impression »).
- **Client rapide** : le vendeur crée un client (nom, téléphone facultatif) sans quitter la vente ; il ne fixe jamais de plafond de crédit (la RLS l'interdit).
- **Limites connues** : le panier n'est pas conservé si la page est rechargée (mode hors ligne et brouillons : étape 11). La rapidité « 3 articles en moins de 10 secondes » et le parcours complet seront mesurés par les tests de bout en bout (étape 12). La concurrence réelle (deux vendeurs, dernier article) reste testée en séquence ici.
- **Piège corrigé** : un test de caisse comptait la journée en UTC alors que la base la compte en heure de Douala ; il échouait entre 23 h et minuit UTC. Les tests utilisent désormais le fuseau de Douala.

## Étape 6 : historique des reçus, annulation, page publique, PDF

- **Historique** (`lister_recus`) : liste paginée par curseur (date + id), 30 par page, du plus récent au plus ancien. Recherche par numéro (même partiel), nom du client (sans accents), téléphone ou montant exact ; filtres statut, vendeur (propriétaire seulement), dates en jours de Douala. Exécutée avec les droits de l'appelant : la RLS limite aux boutiques autorisées. **Défaut trouvé par les tests et corrigé** : la recherche « % » renvoyait tous les reçus (un téléphone vide correspondait à un motif vide). La recherche par téléphone ne s'applique plus qu'aux saisies purement numériques d'au moins 3 chiffres.
- **Immutabilité** : aucun écran, aucune fonction et aucun droit ne permet de modifier ou supprimer un reçu ; les déclencheurs SQL arrêtent même la clé service_role (testé). Les corrections passent par un avoir.
- **Annulation** : réservée au propriétaire, motif obligatoire, confirmation avant envoi. Le reçu reste dans la liste et sur la page, marqué ANNULÉ, avec le numéro de l'avoir et le motif (visibles dans l'application, pas sur la page publique).
- **Ordre des lignes** : `vente_lignes.ordre` garde l'ordre du panier (les lignes sont traitées par produit pour verrouiller le stock dans un ordre fixe). Cela a modifié la migration 3 : toujours possible car rien n'est déployé.
- **Page publique `/r/[jeton]`** : jeton de 64 caractères hexadécimaux (256 bits, non devinable), lecture seule par la fonction `recu_public` (anon peut l'appeler, mais aucune table). Contenu : boutique, lignes, remise, total, paiements, reste à payer, nom du client. **Jamais** : marge, prix d'achat, téléphone du client, identifiants internes, motif d'annulation (testé). Pas d'indexation (`noindex`). Pas de cache applicatif pour l'instant (`use cache` retiré avec Cache Components, voir étape 1) : chaque ouverture lit la fonction `recu_public`, qui est légère. Un cache partagé est prévu à l'étape 21.
- **PDF** (`pdf-lib`, 100 % JavaScript donc compatible Workers) : une page de 300 pt de large, aussi haute que nécessaire, lisible sur téléphone. Police standard : les caractères qu'elle ne sait pas écrire sont remplacés (jamais de plantage). Le test relit le texte du PDF généré.
- **Partage WhatsApp par le vendeur** : sur Android, le PDF part comme fichier via le menu de partage ; sinon lien `wa.me` (numéro du client si connu) avec le résumé et le lien public. Le PDF est préchargé pour que le geste reste immédiat. Aucun appel à Zernio.
- **Reçu en cache pour les liens** : `NEXT_PUBLIC_APP_URL` fixe l'adresse des liens partagés (sinon déduite de la requête).
- **Limites connues** :
  - **Logo** : fait avec la section 10.
  - **Test réel du partage** : le partage de fichier est une API du navigateur : la logique est écrite mais seul un vrai téléphone Android la prouve (étape 12).
  - **PDF sur Workers** : le build Cloudflare passe, mais le PDF n'a pas été exécuté dans `workerd` ici : à vérifier avec `npm run preview` avant le déploiement.

## Étape 7 : clients et crédits

- **Un paiement, plusieurs dettes** : un client qui doit plusieurs ventes paie en une fois. `rembourser_client` répartit le paiement sur ses dettes **les plus anciennes d'abord** (départage par identifiant à date égale), avec **un seul reçu de paiement** (`P-année-n`) partagé par toutes les lignes. Le vendeur voit un aperçu avant de valider (« R-… : soldé », « il restera… »). L'aperçu TypeScript est **comparé à la base** par un test sur un cas réel : même répartition.
- **Jamais deux fois** : chaque paiement porte une clé d'idempotence (index unique par vente soldée). Côté écran, la clé suit le contenu (montant + mode) : un double clic ou un nouvel essai après coupure réutilise la même clé, mais changer le montant en génère une nouvelle, pour qu'un paiement déjà enregistré ne remplace pas en silence le nouveau.
- **Verrou avant calcul** : les dettes du client sont verrouillées avant de calculer ce qu'il doit, pour que deux paiements simultanés se suivent au lieu de se chevaucher. Tout est dans une transaction : un échec n'écrit rien, pas même le numéro de reçu (testé).
- **Garde-fous** : montant > 0 et ≤ dette, client sans dette refusé, mode contrôlé, compte suspendu en lecture seule, client d'une autre organisation refusé. Les espèces entrent dans la caisse du jour, pas le Mobile Money (testé). Chaque paiement est journalisé.
- **« Qui me doit de l'argent »** (`lister_dettes`) : un client par ligne, total des dettes et nombre de clients, tri par montant ou par ancienneté de la plus vieille dette, pagination. Au-delà de 30 jours, la dette est mise en évidence.
- **Rappel WhatsApp** : message courtois, précis (montant, reçus concernés), qui propose des solutions (passer ou payer en Mobile Money). Un test garantit l'absence de ton menaçant (« retard », « impayé », « urgent »…). Il s'ouvre depuis le téléphone du vendeur : **aucun envoi automatique**, aucun appel à Zernio.
- **Clients** : tout membre peut créer un client ; seul le propriétaire modifie, fixe un plafond de crédit (vide = plafond de la boutique) ou archive (la base le refuse aussi au vendeur). **Un client qui doit de l'argent ne peut pas être archivé** (déclencheur SQL). Recherche sans accents par nom ou téléphone, pagination par curseur.
- **Reçu de paiement** : à l'écran, par WhatsApp (texte) et imprimable si le plan l'autorise. PDF ajouté avec la section 10.
- **Fiche client** : dette, plafond et crédit encore disponible, dettes en cours, derniers paiements (regroupés par reçu), 20 derniers achats (les annulés restent visibles).
- **Limites connues** :
  - **Paiement d'une vente précise** : l'écran paie toujours dans l'ordre d'ancienneté. La fonction `enregistrer_remboursement` (une vente à la fois) existe en base mais n'a pas d'écran.
  - **Suivi des rappels** : l'application n'enregistre pas qui a été relancé et quand. À envisager avec les retours des premiers patrons.
  - **Trop-perçu** : un paiement supérieur à la dette est refusé (pas d'avance ni d'avoir client).
- **Piège évité** : PostgreSQL n'a pas de `min()` sur les identifiants uuid (erreur trouvée par les tests) ; et un test donnait des dettes à la même date, ce qui rendait l'ordre « plus ancienne d'abord » indéfini : les tests utilisent maintenant des dates distinctes.

## Étape 8 : caisse et dépenses (section 9.6)

- **Dépenses par une fonction atomique** (`enregistrer_depense`) et plus par écriture directe : droits, lecture seule d'un compte suspendu, validation (montant 1 à 100 000 000 FCFA, catégorie, mode, note 200 caractères), journal `depense_enregistree` et idempotence par clé (verrou par clé : deux envois simultanés ne créent qu'une dépense). L'insertion directe est retirée aux utilisateurs. Une dépense ne se modifie jamais, sauf pour être **annulée** (voir plus bas) ; elle ne se supprime pas.
- **Salaire réservé au propriétaire** : le prompt dit que le vendeur saisit ses « dépenses simples ». J'ai donc retiré la catégorie « Salaire » au vendeur (écran et base).
- **Une dépense peut être payée en Mobile Money** : elle compte dans les dépenses du jour mais ne sort pas du tiroir (seules les dépenses en espèces diminuent les espèces attendues).
- **Clôture** : refusée pour une date future (la journée n'est pas finie) et pour une date de **plus de 30 jours** (reprise de l'étape 8 d'origine ; exactement 30 jours reste accepté). Un jour passé non clôturé peut l'être (un vendeur qui a oublié hier). Écart = compté − attendu (négatif : il manque). L'alerte se déclenche **au-delà** de la tolérance de la boutique, jamais à égalité (même règle côté écran et côté base, testée). Une confirmation est demandée avant d'envoyer, car la clôture ne se modifie plus.
- **Espèces attendues négatives possibles** : si les dépenses en espèces du jour dépassent les encaissements (par exemple un salaire payé sans vente), l'attendu est négatif. C'est affiché tel quel et signale un fond de caisse à reconstituer ; ce n'est pas bloqué.
- **Mouvements après clôture** : une **vente** (ou un paiement de crédit) saisie après la clôture du jour n'est pas refusée (le commerce continue). La page affiche alors « la caisse attendue est maintenant de X » à côté du résultat figé de la clôture. Une **dépense**, en revanche, est refusée une fois la journée clôturée (elle changerait des chiffres déjà comptés) : elle se saisit le lendemain, et l'écran remplace le formulaire par ce message. _Changement par rapport à l'étape 9 d'origine, qui l'acceptait._
- **Annulation d'une dépense** (reprise de l'étape 8 d'origine) : `annuler_depense`, propriétaire seulement, motif obligatoire (200 caractères), impossible une fois la journée de la dépense clôturée. La dépense reste visible, barrée, avec son motif, et ne compte plus dans la caisse (`calculer_caisse` l'exclut). Un déclencheur SQL n'autorise que ce passage (jamais d'autre modification, même pour la clé service_role). Journal `depense_annulee` (catégorie Caisse, journal complet, **marquée alerte**). Le journal de base (plan Essentiel) n'y a pas accès, comme pour `depense_enregistree`.
- **Défaut corrigé dans la caisse** : le Mobile Money d'une vente annulée restait compté comme encaissé. `calculer_caisse` renvoie désormais aussi `mtn_momo_rembourse` et `orange_money_rembourse` (ventes annulées ce jour-là) ; l'écran affiche le Mobile Money net. Le Mobile Money reste « suivi à part » : il n'entre pas dans le tiroir.
- **Résumé du jour** : ventes (nombre et total), espèces, MTN, Orange, crédit accordé, dépenses, et le détail du calcul des espèces attendues. Tout est calculé par la base ; l'écran ne recalcule rien. Journée en heure de Douala (testé : 23 h 30 UTC est déjà le lendemain).
- **Historique** : 14 dernières clôtures, avec lien vers le jour. Le propriétaire voit « À valider » en tête de page et valide en un bouton. Les dépenses ne se saisissent que pour le jour même.
- **Limites connues** : une seule boutique par compte jusqu'à l'étape 16 (le sélecteur de boutique viendra avec). Un vendeur ne voit le nom d'un collègue que s'il a le droit de le lire (sinon la ligne n'affiche pas d'auteur). Les écrans ne sont pas encore couverts par un test de bout en bout (étape 12).

## Étape 9 : tableau de bord, journal et alertes (sections 9.7 et 9.8)

- **Un seul appel pour le tableau de bord** : `tableau_de_bord(boutique)` renvoie tout (ventes du jour et d'hier, caisse, dettes, stock bas, ventes par vendeur, produits vendus, clôtures à valider). Réservé au propriétaire, vérifié dans la base. Aucune marge ni prix d'achat n'y figure (testé) : la marge relève du rapport, pas de l'écran d'accueil.
- **Produits les plus vendus** : sur 7 jours glissants, classés par chiffre d'affaires, quantité en unité de base, ventes annulées exclues. Le prompt ne précise pas la période : 7 jours donne un classement stable (un seul jour est trop bruité pour une quincaillerie).
- **Stock bas** : même règle que l'alerte (stock < seuil, seuil > 0), produits archivés ou inactifs exclus. Le tableau montre les 5 plus bas, avec un lien vers la liste complète filtrée.
- **Temps réel** : abonnement Supabase Realtime sur `ventes`, `paiements`, `depenses` et `clotures_caisse`, filtré par boutique. La RLS décide ce que chaque connexion reçoit. Les événements rapprochés sont regroupés (une vente écrit dans deux tables, un seul rafraîchissement). Si le temps réel est coupé ou en échec : repli sur une actualisation toutes les 30 s. Onglet caché : abonnement et minuteur coupés, puis actualisation immédiate au retour. L'état est affiché (« En direct », « Actualisation toutes les 30 secondes », « En pause »). La règle de mode est une fonction pure testée.
- **Publication Realtime** : la migration ajoute les 4 tables à `supabase_realtime` si elle existe (sans effet sur la base de test). **À vérifier au premier déploiement** : que Realtime est bien activé sur le projet Supabase. Sans lui, le repli de 30 s prend le relais, rien ne casse.
- **Sélecteur de boutique** : affiché seulement pour un plan qui permet plusieurs boutiques ET s'il y en a plusieurs. Aujourd'hui aucun compte n'en a deux (étape 16) : il est prêt mais invisible. Le tableau consolidé relève de l'étape 16.
- **Journal** : page propriétaire, du plus récent au plus ancien, pagination par curseur (date + identifiant, stable même si des lignes arrivent pendant la lecture), 30 lignes par page. Filtres : type, période (en jours de Douala), alertes seulement. `lister_journal` s'exécute avec les droits de l'appelant : la RLS limite au journal de base ou complet selon le plan, et demander une action réservée au plan supérieur ne la révèle pas (testé). Le filtre n'affiche que les types permis par le plan, sans bouton verrouillé ni incitation.
- **Sécurité du curseur** : il vient de l'adresse, il est validé strictement (date ISO + entier) et transmis comme paramètres typés, jamais assemblé dans un filtre texte.
- **Deux garde-fous de test** : (1) chaque action que la base écrit dans le journal doit avoir un libellé français ; (2) la liste « journal de base » du code doit être identique à la politique RLS du plan Essentiel. Si quelqu'un ajoute une action ou change la politique sans mettre l'autre à jour, la CI échoue.
- **Textes du journal** : phrases construites à partir des détails, sans jamais planter si un détail manque. Affichés comme du texte simple (React échappe tout), donc un motif contenant du HTML reste inoffensif.
- **Logo** : le logo fourni (main « OK » en éventail, orange #F35D27) est ajouté en en-tête de la barre latérale et comme icône du site. Le fichier reçu fait 440 × 464 px : suffisant pour l'en-tête, trop petit pour l'icône PWA 512 px de l'étape 11, où il faudra le logo en vectoriel (SVG) ou en 1024 px.
- **Limites connues** : pas encore de test de bout en bout des écrans (étape 12). Les chiffres sont ceux d'une seule boutique à la fois.

## Étape 9 (suite) : paramètres de la boutique (section 9.9)

- **Réglages par fonction atomique.** `modifier_parametres_boutique` remplace l'écriture directe sur `boutiques` et `parametres_boutique` (UPDATE révoqué, politiques supprimées). Avant, un propriétaire dont le compte était suspendu pouvait encore modifier ses réglages, sans validation fine ni journal. La fonction vérifie le rôle (propriétaire seul), la lecture seule, les bornes, puis écrit le journal.
- **Journal `parametres_modifies`** (catégorie Compte, journal complet). Il liste les champs modifiés ; pour les règles (remise, plafond, stock négatif, écart toléré) il garde avant/après. Les coordonnées de la boutique n'y sont pas copiées. Si rien ne change, rien n'est écrit.
- **Plafond de crédit par défaut** : il s'applique aux nouveaux clients seulement. Les clients existants gardent leur plafond, sinon un réglage ferait changer des dettes en cours.
- **Mon abonnement** : plan, état en langage clair, prochaine échéance, 12 derniers paiements. On montre le montant brut ; les frais de paiement (Fapshi) ne regardent pas le client. Aucun bouton de paiement avant l'étape 18 (Fapshi).
- **Test du vocabulaire du journal** : il lit désormais toutes les migrations, pour qu'une nouvelle action ne puisse plus être oubliée dans une liste figée.
- Section 9.9 complète : boutique, pied de reçu, règles, vendeurs (déjà là), abonnement.

## Section 10 : reçus, logo et impression

- **Un seul modèle de reçu** (`lib/print/document.ts`, `DocumentRecu`) pour le PDF, le ticket ESC/POS, le ticket 58 mm et la facture A4 du navigateur. Il existe pour les ventes et pour les paiements de crédit (qui ont donc maintenant PDF, partage de fichier et impression). Jamais de coût d'achat ni de marge dedans (testé).
- **`imprimerRecu(recu, format, env)`** (`lib/print/index.ts`) est le seul point d'entrée : remplacer RawBT par une application Android native ne touchera que ce dossier. Ordre : (1) Android + ticket : octets ESC/POS vers RawBT ; (2) boîte d'impression du navigateur (ticket ou A4) ; (3) PDF. Elle ne lève jamais d'erreur : en cas d'échec complet, message « la vente est bien enregistrée » et bouton **Réessayer**. L'environnement (navigateur, Android) est injecté : tout le parcours est testé sans téléphone.
- **RawBT** : lien `intent:base64,<octets>#Intent;scheme=rawbt;package=ru.a402d.rawbtprinter;end;` (schéma `rawbt:base64` documenté sur rawbt.ru ; la forme `intent:` nomme le paquet, Android propose l'installation si RawBT manque). Le ticket est préchargé au chargement de l'écran pour que le tap parte tout de suite (Chrome exige un geste récent).
- **ESC/POS 58 mm, 32 colonnes** : mise en page pure et testée (jamais plus de 32 caractères par ligne, montants alignés à droite, noms longs passés à la ligne). Sans accents par défaut : on ne peut pas savoir quelle page de code une imprimante a en mémoire, et un mauvais choix imprime des signes illisibles. Réglage par appareil « Mon imprimante affiche les accents » : active la page 858 (`ESC t 19`).
- **Plan appliqué côté serveur** : le ticket ESC/POS vient de routes (`/vente/recu/[id]/escpos`, `/clients/[id]/paiement/[numero]/escpos`) qui refusent (403) un plan sans impression via `accesImpression` (testé pour chaque rôle) ; les documents A4/ticket ne sont même pas rendus dans la page pour un plan Essentiel.
- **Impression navigateur** : `@page` ne dépendant pas d'un attribut, une feuille de style est posée le temps de l'impression et `data-impression` choisit le document. Le ticket n'a **pas** de `size` : Chrome ne comprend pas `58mm auto`, le papier vient donc de l'imprimante et la largeur (58 mm) est fixée en CSS. Rendu vérifié avec Chromium (une page, application masquée) pour la vente, la vente longue annulée et le paiement.
- **Logo** : PNG, 300 px de large, 40 Ko maximum, réduit sur le téléphone par paliers (le PNG n'a pas de réglage de qualité) avec transparence conservée ; clé `<organisation>/<hash>-l.png` en base (`boutiques.logo_cle`, migration 12, contrainte de forme), contrôlée côté serveur comme les photos (clé de son organisation, taille, signature PNG). Propriétaire seulement : écrit par la fonction `definir_logo_boutique` (rôle, compte en lecture seule, clé de sa propre organisation, journal `parametres_modifies` avec le champ `logo`), l'`UPDATE` direct sur `boutiques` ayant été retiré à l'étape 9 (testé). Affiché sur le reçu, le PDF, le ticket navigateur et la facture A4. Un logo illisible est ignoré : il ne bloque jamais un reçu. Seul identifiant exposé dans le reçu public : la clé du logo (qui contient l'identifiant d'organisation, sans valeur d'accès).
- **Limites connues** :
  - **Aucune imprimante réelle testée** : l'encodage ESC/POS est testé octet par octet, mais RawBT et l'imprimante Bluetooth ne se prouvent que sur un vrai téléphone Android (étape 12). À vérifier en particulier : que RawBT transmet les octets tels quels, et la page de code 858.
  - **Pas de logo sur le ticket thermique** : il faudrait une image bitmap ESC/POS ; le ticket imprime le nom de la boutique en grand. Le logo figure sur le PDF, l'écran, le ticket navigateur et l'A4.
  - **Facture A4** : le titre « Facture » suit le prompt ; les mentions légales (NIU, RCCM…) passent par le pied de reçu, dont l'écran de saisie viendra avec les paramètres de la boutique. Valeur juridique à faire valider.
  - **Cache de la page publique** : le cache `use cache` de `lireRecuPublic` a été retiré du dépôt avant cette étape (modification faite en dehors de cette session) ; le PDF public garde `Cache-Control: public, max-age=60`.
  - **Zernio** : hors parcours de vente, comme exigé (utilisé aux étapes 17 et 18 seulement).
