# Photos des produits (Cloudflare R2)

Les photos ne passent jamais par Supabase Storage. Parcours :

1. Le navigateur réduit la photo (WebP, 800 px, moins de 100 Ko) et la vignette (200 px, moins de 15 Ko).
2. Le serveur vérifie le rôle (propriétaire) et signe une URL d'envoi valable 5 minutes, pour une seule clé `organisation/empreinte.webp`.
3. Le navigateur envoie le fichier directement vers R2.
4. À l'enregistrement du produit, le serveur contrôle le fichier (existe, taille, vrai WebP) et le supprime s'il est invalide. La base ne garde que la clé.
5. Les photos sont servies par `/img/<clé>` (lecture dans R2 par l'API S3, cache d'un an côté navigateur et CDN Vercel, nom de fichier = empreinte du contenu).

## Mise en place

1. Créer le bucket `kaya-images` dans le tableau de bord Cloudflare (R2 reste utilisé, seul l'hébergement de l'application change).
2. Créer une clé d'API R2 (lecture et écriture, limitée à ce bucket).
3. Enregistrer `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET` dans les variables d'environnement Vercel.
4. Autoriser l'envoi depuis le navigateur (CORS du bucket), en remplaçant l'adresse par celle de l'application :

```json
[
  {
    "AllowedOrigins": ["https://app.exemple.cm"],
    "AllowedMethods": ["PUT"],
    "AllowedHeaders": ["content-type"],
    "MaxAgeSeconds": 3600
  }
]
```

5. En local : renseigner les variables `R2_*` dans `.env.local`. Sans secrets R2, l'application fonctionne mais l'ajout de photo est refusé avec un message clair.

## Limites connues

- Une URL signée ne peut pas plafonner la taille du fichier : le contrôle se fait après l'envoi (et le fichier invalide est supprimé). Un fichier envoyé mais jamais rattaché à un produit reste dans le bucket : prévoir un nettoyage planifié à l'étape 21.
- Pas de limitation de débit sur la demande d'URL signée pour l'instant (réservée au propriétaire connecté) : limitation de débit (Vercel Firewall) à ajouter avant l'ouverture au public.
